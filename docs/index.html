anvil

An embedded, LSM-tree-based key-value storage engine, written in Java.

View source on GitHub →

The kind of engine that sits underneath a database, not one with a query language on top. No server, no SQL: you embed it as a library and call put(key, value) / get(key) / delete(key) directly, the same way RocksDB or LevelDB get embedded inside larger systems.

Built in five phases, each independently verified and committed: durable writes, disk-backed storage, compaction, thread-safe concurrent access, and JMH-benchmarked performance.

Architecture

flowchart TD Client(["Client: put / get / delete"]) Client -->|put/delete| WAL["Write-Ahead Log
fsync before ack"] WAL --> MemTable["MemTable
ConcurrentSkipListMap"] MemTable -->|"size >= threshold"| Flush["Flush"] Flush --> NewSST["new sstable-NNNN.db"] Flush -.clears.-> MemTable Flush -.truncates.-> WAL NewSST --> CompactCheck{"2+ SSTables?"} CompactCheck -->|yes| Compactor["Compactor
merge + drop tombstones"] Compactor --> MergedSST["single merged SSTable"] CompactCheck -->|no| Idle["wait for next flush"] Client -->|get| ReadMem{"key in MemTable?"} ReadMem -->|yes| ReturnMem["return value / null if tombstoned"] ReadMem -->|no| ReadSST["scan SSTables newest to oldest"] ReadSST --> ReturnSST["return first match / null"]

Write path: every put/delete is appended to the WAL and fsync'd to disk before the call returns, then applied to an in-memory sorted MemTable. If the process crashes between those two steps, replaying the WAL on restart reconstructs the exact state.

Compaction merges SSTables into one file once enough accumulate, keeping the newest version of each key and dropping tombstones entirely.

Concurrency: ordinary reads/writes take a shared read lock; only flush/compaction takes an exclusive write lock.

Benchmarks

Measured with JMH (3 warmup + 5 measurement iterations, single fork):

BenchmarkThroughput (ops/s)
writeThroughput893.652 ± 202.206
readFromMemtable2,091.694 ± 95.638
readFromSSTable88,524.118 ± 502.499
readMixed4,156.447 ± 6,174.625

Write throughput (~890 ops/s) is fsync-bound by design.

Read throughput varies ~40x depending on where a key physically lands. This is the honest cost of a linear-scan SSTable lookup, and the direct motivation for a bloom filter or sparse index.

Also verified under concurrent load: 8 threads × 500 writes (4,000 total operations) completed in 625ms with zero errors and zero data mismatches.

Running it

javac -d out $(find src/main/java -name "*.java")
java -cp out com.anvil.Main
java -cp out com.anvil.Main recover
mvn clean package -q
java -jar target/benchmarks.jar

What's next

  • Bloom filters — skip SSTables that provably don't contain a key
  • Sparse index per SSTable — near-constant-time lookups
  • Range scans — iterate sorted keys across MemTable + SSTables
  • Leveled compaction — bound compaction cost as data grows
